# Production migration plan: canceled Stripe subscription rebind

**Status: proposal only. No production SQL has been applied or approved.** Source: `supabase/migrations/20261031185027_allow_canceled_stripe_subscription_rebind.sql`. It replaces `public.app_apply_stripe_subscription_event(text,text,timestamptz,uuid,text,text,text,timestamptz)` so a newer, signed active Checkout for the same Stripe customer can replace a canceled subscription. Late events for the old subscription remain stale. It was tested and applied to isolated staging after separate approval; that is not production evidence.

## Known mismatch and preflight

The approved November 8 production snapshot found a compatible **signature**, but did not inspect the function body. The repository migration version was absent from the production migration history. Therefore the behavioral delta is unknown. Fresh approved `supabase-ci` metadata must establish the exact signature, security mode, search path, execute grants, dependent functions/triggers and migration history. Capture the live function body and ACL securely outside the repo for an exact rollback; do not paste a body or sensitive values into this report. Compare the body in a controlled review before deciding whether a new reconciliation migration is needed at all.

An isolated-staging acceptance with synthetic Stripe TEST identities must cover canceled-to-active same-customer rebind, rejection of a different customer or tenant, late old-subscription events, duplicate event IDs, out-of-order timestamps, concurrent webhook delivery, and `past_due`/cancellation access. Keep production billing disabled until merchant/legal, price and webhook configuration are separately accepted.

## Verification query

Run only through the approved read-only `supabase-ci` before and after any separately approved change. This checks metadata and grants; behavior still needs staging evidence. The function body is intentionally omitted from this report query.

```sql
select n.nspname as schema_name, p.proname as function_name,
       pg_catalog.pg_get_function_identity_arguments(p.oid) as identity_arguments,
       pg_catalog.pg_get_function_result(p.oid) as result_type,
       p.prosecdef as security_definer,
       p.proconfig as function_settings,
       p.proacl as execute_acl,
       pg_catalog.has_function_privilege('anon', p.oid, 'EXECUTE') as anon_execute,
       pg_catalog.has_function_privilege('authenticated', p.oid, 'EXECUTE') as authenticated_execute,
       pg_catalog.has_function_privilege('service_role', p.oid, 'EXECUTE') as service_execute
from pg_catalog.pg_proc p
join pg_catalog.pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public'
  and p.proname = 'app_apply_stripe_subscription_event'
order by 1, 2, 3;
```

Require one exact eight-argument overload, `SECURITY DEFINER` with fixed empty `search_path`, no `PUBLIC`/`anon`/`authenticated` execute path and a reviewed `service_role` execute grant. Record a controlled hash of the live function definition before and after in the operator's private review evidence; signature equality alone cannot prove the rebind logic.

## Rollback

Pause webhook processing through a **separately approved** operational change and preserve signed event delivery for replay. In a reviewed transaction, restore the exact captured pre-change function body, settings and ACL; do not replace it with the repository's older staging body by assumption. Resume only after synthetic staging and metadata verification. This restores future event behavior but cannot undo a subscription rebind already accepted or delete an event safely. Reconcile affected Stripe/app bindings and any duplicate or late events individually under a separate written decision; preserve audit/webhook history.

## Approval gate

The reviewer needs the live-body comparison, current migration history and grants, exact proposed SQL/hash, captured rollback body, staging Stripe TEST results and customer-impact assessment. Obtain written approval for this particular production write. This plan authorizes none.
