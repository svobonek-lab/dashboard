# Production migration plan: monthly tariffs

**Status: proposal only. No production SQL has been applied or approved.** This plan covers two dependent repository files: `supabase/migrations/20261101131053_three_tier_monthly_plans.sql` and `20261101140813_three_tier_company_plan_check.sql`. They must be reviewed as separate ordered steps under one tariff release. The first extends paid-registration intents and replaces two service functions; the second extends `app_companies.plan` while preserving legacy `business`.

## Known mismatch and preflight

The approved November 8 production snapshot found a six-argument `app_prepare_paid_registration` and **no** `app_companies_plan_check`. The second repository file explicitly requires a particular old definition of that constraint and will abort against that snapshot. Neither file is a production-ready migration. First obtain fresh approved `supabase-ci` metadata for `app_companies`, `app_paid_registration_intents`, their check constraints, the exact six-argument registration function, `app_platform_set_billing_plan(uuid,uuid,text)`, execute grants and migration history. Capture the prior function definitions and ACLs securely outside the repo for rollback. Confirm any existing `growth`, `pro` and legacy `business` plan values with an approved aggregate-only check before changing constraints.

The intended order after new review is: (1) reconcile the live paid-intent check and registration RPC without an ambiguous callable overload; (2) reconcile the live company plan constraint without assuming it already has the source name or definition; (3) test full billing and access lifecycle on disposable PostgreSQL and isolated staging with synthetic companies; (4) request written approval for each production SQL write. Do not enable paid registration or configure production price IDs as a side effect.

## Verification query

Run this read-only **metadata query through approved `supabase-ci`** immediately before and after any separately approved step. Record the complete rows and compare them to the exact reviewed candidate. A returned row alone does not prove function behavior.

```sql
select 'constraint' as object_kind, n.nspname || '.' || c.relname as object_name,
       co.conname as detail, pg_catalog.pg_get_constraintdef(co.oid) as definition
from pg_catalog.pg_constraint co
join pg_catalog.pg_class c on c.oid = co.conrelid
join pg_catalog.pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public' and c.relname in ('app_companies', 'app_paid_registration_intents')
  and co.contype = 'c'
union all
select 'function', n.nspname || '.' || p.proname,
       pg_catalog.pg_get_function_identity_arguments(p.oid),
       pg_catalog.pg_get_function_result(p.oid)
from pg_catalog.pg_proc p
join pg_catalog.pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public'
  and p.proname in ('app_prepare_paid_registration', 'app_platform_set_billing_plan')
order by 1, 2, 3;
```

An approved staging acceptance must additionally prove `starter`, `growth` and `pro` choices, rejection of new Pilot subscriptions, idempotent retry, legal-consent and verified-identity checks, legacy `business` compatibility, correct Stripe webhook activation/cancellation, and no browser execute grant on service functions. Existing disposable tests in `.github/workflows/verify.yml` and `supabase/tests/three_tier_monthly_plans_verify.sql` are useful evidence but do not replace the live-schema preflight.

## Rollback

Freeze new paid-registration and plan-change calls first. Restore the **captured pre-change** function definitions and execute ACLs in a separately reviewed transaction; remove only the new seven-argument overload after callers are switched back. Restore each pre-change constraint only after confirming it accepts all currently stored plan values. If `growth` or `pro` has been assigned, a blind return to a narrower check would fail or strand customers; retain a compatibility constraint and use a separately approved forward correction or customer-specific remediation. Do not delete paid intents, company plans, subscriptions or webhook history. Verify restored signatures, constraints and grants with the query above and repeat synthetic staging billing tests before resuming traffic.

## Approval gate

The reviewer must receive a fresh full production metadata comparison, the new reconciliation SQL and hash, captured rollback definitions, aggregate data-compatibility result, isolated-staging evidence and customer impact. Written approval of **each** production write is still required. This document is not that approval.
